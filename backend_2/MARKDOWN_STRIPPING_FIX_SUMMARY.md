# Markdown Code Block Stripping Fix - Summary

## Problem
LLM-generated HTML content (autogenerated summaries, timeline event descriptions, and property/relationship justifications) was being wrapped in markdown code block delimiters like:
```html
<article>
  <h2>Content</h2>
</article>
```

This made the content unparsable on the frontend.

## Solution
Added markdown code block stripping functionality throughout the architect.generate_entities pipeline.

## Changes Made

### 1. Core Functionality
- Added `_strip_markdown_code_blocks()` function in both:
  - `app/tasks/architect_generation_v2.py`
  - `app/jobs/architect/entity_generator.py`
- Defined `MARKDOWN_CODE_BLOCK_PATTERN` constant: `r"```[a-zA-Z]*\s*\n?(.*?)\n?```"`
- Updated type annotations to `str | None` to accurately reflect None handling

### 2. Application Points

#### architect_generation_v2.py
- **Autogenerated summaries**: Applied in `_compose_autogenerated_summaries()`
- **HTML formatting**: Applied in `_maybe_structure_summary_html()`
- **Chunk parsing**: Applied when parsing summaries, property values, and relationship justifications
- **Timeline events**: Applied in `_normalize_timeline_event_entry()` for titles and descriptions

#### entity_generator.py
- **Property extraction**: Applied in `_parse_extraction_response()` for:
  - `autogenerated_summary`
  - `updated_autogenerated_summary`
  - Relationship justifications
  - Property text values

### 3. Coverage
The fix covers:
- ✅ Autogenerated entity summaries
- ✅ Timeline event titles and descriptions
- ✅ Property values (text type)
- ✅ Relationship justifications
- ✅ All chunks in the pipeline
- ✅ Chunk merging operations

### 4. Language Support
The regex pattern handles code blocks with:
- HTML: `\`\`\`html`
- JavaScript: `\`\`\`javascript`
- CSS: `\`\`\`css`
- Any language: `\`\`\`[a-zA-Z]*`
- No language identifier: `\`\`\``

## Future Considerations
The code review noted that `MARKDOWN_CODE_BLOCK_PATTERN` and `_strip_markdown_code_blocks()` are duplicated across two modules. While this is a valid observation, extracting to a shared utility module would be a larger refactoring beyond the minimal scope of this fix. The current implementation is acceptable and ensures consistency through the use of named constants.
