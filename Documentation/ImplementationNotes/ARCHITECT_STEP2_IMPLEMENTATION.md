# Architect Step 2 Implementation Summary

## What Was Implemented

This implementation adds the second step of the architect job workflow for the Shrecknet collaborative world-building platform.

### Problem Statement Summary

The architect job needed a second step where:
1. The client returns validated instances (approved, rejected, or merged proposals)
2. For approved new entities: the system generates properties, relationships, and summaries from text
3. For approved updates: the system adds new properties/relationships and updates summaries
4. The system only creates/updates entities that were approved or merged
5. The process is parallelized for performance
6. Results are tracked so the client can retrieve generated entity IDs

### Implementation Details

#### 1. Database Schema Updates

**New Fields in `architect_proposals` table:**
- `merged_into_proposal_id` - Tracks which proposal this was merged into
- `corrected_alias` - User-corrected entity alias
- `corrected_entity_definition_id` - User-corrected entity type
- `corrected_proposal_type` - User-corrected proposal type (NEW_INSTANCE ↔ UPDATE_INSTANCE)
- `corrected_entity_instance_id` - User-corrected entity instance ID for updates
- `chunks` - Text chunks relevant to this proposal (stored as JSON array)
- `generated_entity_instance_id` - ID of the entity created/updated by this proposal

**New Enum Value:**
- Added `MERGED` to `ArchitectProposalStatus`

**Migration:**
- Added `migrate_architect_proposals()` function in `app/db/migrations.py`
- Automatically runs on database initialization

#### 2. New Schemas

**Request Schema (`ArchitectValidationRequest`):**
```python
{
    "run_id": str,
    "validated_proposals": [
        {
            "proposal_id": str,
            "status": "approved" | "rejected" | "merged",
            "corrected_alias": str | None,
            "corrected_entity_definition_id": int | None,
            "corrected_proposal_type": "new_instance" | "update_instance" | None,
            "corrected_entity_instance_id": str | None,
            "merged_into_proposal_id": str | None
        }
    ],
    "author_type": str,
    "author_id": str
}
```

**Property Extraction Schemas:**
- `PropertyExtractionResponse` - For new entities
- `PropertyUpdateResponse` - For updating entities
- `ExtractedProperty` - Individual property
- `ExtractedRelationship` - Individual relationship

#### 3. Entity Generator (`app/jobs/architect/entity_generator.py`)

**Class: `EntityGenerator`**

Key Methods:
- `generate_new_entities()` - Creates new entities from approved proposals
- `update_existing_entities()` - Updates existing entities with new data
- `add_relationships_to_entities()` - Second phase: adds relationships after entities exist
- `_extract_properties_and_relationships()` - Uses LLM to extract data from text

Features:
- Parallel processing using asyncio semaphores
- Handles corrected aliases and entity definitions
- Only extracts auto-generatable properties/relationships
- Generates concise autogenerated_text summaries
- Validates target entities exist before creating relationships

#### 4. Background Task (`app/tasks/architect_generation.py`)

**Celery Task: `generate_entities`**

Workflow:
1. Update proposals with validation data (status, corrections, merges)
2. Filter to approved/merged proposals (skip rejected)
3. Load ontology metadata (entity definitions, properties, relationships)
4. Get original instance text for context
5. **Phase 1**: Generate new entities (without relationships)
6. **Phase 1.5**: Add new entities to the instance in Neo4j
7. **Phase 2**: Update existing entities with new properties/relationships
8. Track created/updated entity IDs in job results

Features:
- Progress tracking via background job
- Error handling and logging
- Stores entity IDs in proposals for client retrieval

#### 5. API Endpoint

**POST `/api/jobs/architect/runs/{run_id}/generate`**

Accepts validated proposals and starts the entity generation task.

Returns:
```json
{
    "status": "accepted",
    "task_id": "celery-task-id",
    "run_id": "run-uuid",
    "message": "Entity generation task started"
}
```

#### 6. Updated Step 1

Modified `ArchitectOrchestrator._aggregate_results()` to:
- Track text chunks for each proposal
- Store chunks in the `chunks` field of proposals

This allows step 2 to have the relevant text for each entity.

#### 7. LLM Prompts

**New Prompts:**
- `ARCHITECT_PROPERTY_EXTRACTION_PROMPT` - Extract properties/relationships for new entities
- `ARCHITECT_PROPERTY_UPDATE_PROMPT` - Extract new properties/relationships for updates

Prompts instruct the LLM to:
- Only extract information present in the text
- Not invent information
- Generate concise, complete summaries
- Identify relationships to other entities

#### 8. Repository Methods

**Added to `ArchitectRepository`:**
- `update_proposal_validation()` - Update proposal with validation data
- `update_proposal_generated_entity()` - Store generated entity ID
- `get_proposals_by_ids()` - Fetch specific proposals
- `get_proposals_by_run()` - Fetch all proposals for a run

## How to Use

### Step-by-Step Workflow

1. **Client requests analysis (Step 1):**
   ```
   POST /api/jobs/architect/{agent_id}/analyze
   ```

2. **Client polls for completion:**
   ```
   GET /api/jobs/architect/runs/{run_id}
   ```

3. **Client reviews proposals and prepares validation:**
   - Display proposals to user
   - User approves, rejects, or merges proposals
   - User can correct aliases or entity types

4. **Client submits validated proposals (Step 2):**
   ```
   POST /api/jobs/architect/runs/{run_id}/generate
   ```

5. **Client tracks generation progress:**
   ```
   GET /api/jobs/background/{job_id}
   ```

6. **Client retrieves results:**
   ```
   GET /api/jobs/architect/runs/{run_id}
   - Check generated_entity_instance_id on proposals
   
   GET /api/ontology/instances/{instance_id}
   - View updated instance with new entities
   ```

## Key Design Decisions

1. **Two-Phase Processing**: Entities are created before relationships to handle forward references (entity A references entity B that hasn't been created yet).

2. **Chunks Storage**: Step 1 now stores relevant text chunks with each proposal so step 2 has context for extraction.

3. **Correctable Proposals**: Users can fix typos or change entity types before generation.

4. **Merge Support**: Duplicate proposals can be merged into a main proposal, reducing duplication.

5. **Selective Extraction**: Only auto-generatable properties/relationships are extracted, respecting the ontology design.

6. **Context-Aware**: The LLM receives both specific chunks and the full original text for better extraction.

7. **Author Tracking**: Entity updates track who made them (user vs agent) for audit purposes.

## Client Capabilities Summary

The client can now:

1. **Approve/Reject/Merge** proposals
2. **Convert proposal types**:
   - NEW_INSTANCE → UPDATE_INSTANCE (when client finds entity already exists)
   - UPDATE_INSTANCE → NEW_INSTANCE (when client realizes it's a new entity)
3. **Change update targets**: Specify different entity to update
4. **Fix entity types**: Change entity definition
5. **Fix aliases**: Correct typos or formatting

All changes are optional - the server uses original values for any null corrected fields.

## Future Enhancements

Potential improvements not included in this implementation:

1. **Batch validation**: Allow validating multiple runs at once
2. **Partial updates**: Allow updating only specific fields of existing entities
3. **Relationship validation**: Preview relationships before creation
4. **Conflict resolution**: Handle cases where the same relationship already exists
5. **Rollback support**: Allow undoing entity generation
6. **More granular progress**: Report progress per entity being processed

## Notes

- The system is designed to be fast through parallelization
- Only entities marked as `auto_generatable` in the ontology will have properties/relationships extracted
- The system will not invent information - it only extracts what's in the text
- Relationships are only created if both source and target entities exist
- The autogenerated_text is designed to be a complete, concise summary suitable for display
