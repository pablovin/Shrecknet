# Ontology-Aware Semantic Embedding V2

Scene-centric memory uses a derived `SemanticDocument` projection. Canonical `EntityInstance`, `Scene`, `Milestone`, and their Neo4j relationships remain the source of truth; semantic documents are disposable retrieval entry points.

Semantic documents are the only supported scene-memory embedding strategy.

## Shared embedding runtime

V2 and Librarian V2 share:

- `embedding_model_id` (default `intfloat/multilingual-e5-small`)
- `embedding_dimension` (default `384`)
- `embedding_device`
- the process-wide model cache and inference gate
- the request-time micro-batching runtime
- E5 `passage:` and `query:` conventions

Their renderers and document graphs remain independent.

## SemanticDocument graph

Canonical graph sources use:

```text
(EntityInstance|Scene|Milestone)-[:HAS_SEMANTIC_DOCUMENT]->(SemanticDocument)
```

Ontology definition documents have no canonical Neo4j source because ontology definitions live in SQL.

Every document stores:

- `document_id`, `source_kind`, `source_node_id`
- `ontology_id`, optional `instance_id`
- optional `entity_definition_id`, `relationship_definition_id`, `scene_id`
- optional `source_field`, `source_text_hash`, `chunk_index`, `chunk_count`
- `related_entity_ids`, `derived_from_entity_id`
- source creation/update dates
- `display_text` and E5-prefixed `embedding_text`
- `content_hash`, `metadata_hash`, `embedding_version`
- embedding model, dimension, vector, and timestamps

Indexes:

- `semantic_document_vec_idx`
- `semantic_document_fulltext_idx`

## Document families

### Ontology entity definitions

One ontology-scoped representation contains the type name and description, property names/descriptions/types/cardinality, and allowed relationships. It lets retrieval interpret world-specific terms without hard-coded Story, Character, or Location classes.

### Ontology relationship definitions

Each definition contains its name, meaning, source type, destination type, and directionality.

### Entity profiles

Every entity receives a compact discovery profile containing its alias, readable ontology type and meaning, meaningful short properties, and short `text`/`autogenerated_text` values.

Profiles never copy neighbour descriptions, entity relationship histories, scenes, or milestones.

### Entity long text

V2 examines `text`, `autogenerated_text`, and ontology properties with SQL data type `TEXT`. Content above 512 tokens becomes ordered `entity_text_chunk` documents. Each chunk retains its source field and source-text hash.

### Scenes

A scene document contains its name, description, directly related aliases, and optional `DERIVED_FROM` alias/type. It does not copy milestones or indirect neighbourhoods.

### Milestones

A milestone document contains its name, description, temporal/boundary classifications, directly related aliases, provenance ID, and containing scene identity.

## Lossless chunking

The configured defaults are a 384-token target and 64-token overlap. Token accounting includes the contextual header and `passage:` prefix.

Splitting proceeds through structural blocks, paragraphs, sentences, and finally explicit tokenizer windows. The embedding model is never asked to truncate. Overflow always produces more documents; it is never discarded. Final documents are checked again before inference for token budget, finite values, and configured vector dimension.

## Freshness and reconciliation

Rendering is deterministic. Inference runs only when one of these changes:

- `content_hash`
- `embedding_version`
- model ID
- vector dimension

Metadata-only changes update the document without regenerating its vector.

| Graph/SQL write | Reconciled V2 sources |
| --- | --- |
| Entity content or property | That entity profile and its text documents |
| Entity relationship edge | No entity inference unless rendered profile changes |
| Scene create/update | That scene; initial nested milestones are separate targets |
| Milestone create/update | That milestone |
| Scene/milestone delete | Delete documents for the missing source ID |
| Ontology entity/property/relationship definition | Affected vocabulary documents and profiles of that entity definition |
| Full ontology trigger | All expected vocabulary and canonical memory documents |

Reconciliation renders and embeds before replacing a source's stored document set. A rendering or inference failure therefore leaves the previous valid set available.

## Retrieval

Vector and full-text hits resolve through `HAS_SEMANTIC_DOCUMENT` to canonical memory nodes. Ontology-definition hits act as a bounded entity-type ranking hint and are not narrative evidence.

After semantic selection, Cypher reads current identity, relationships, provenance, containment, and temporal adjacency from the canonical graph. Vectors never serve as complete memory snapshots.

## Reset and manual migration

`POST /graphrag/embed/ontology/reset` deletes `SemanticDocument` data for the ontology, resets derived embedding flags, and never deletes canonical memory.

Migration procedure:

1. Deploy V2 API and workers.
2. Pause relevant writes/workers if a consistent maintenance window is required.
3. Run the existing reset operation for every ontology containing old embeddings.
4. Trigger full ontology embedding for every ontology.
5. Monitor embedding jobs and `/ontologies/{ontology_id}/embedding-stats`.
6. Verify representative Elder and GraphRAG queries before resuming normal operation.

An empty retrieval window between reset and rebuild is expected.
